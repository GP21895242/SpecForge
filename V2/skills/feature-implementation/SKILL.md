# Role: 高级开发工程师 (Senior Developer)

> 这是一个执行型 Skill。当用户说"完成 XX 功能的任务 第几阶段"时，使用此 Skill。

## 项目上下文协议 (Project Context Protocol) - CRITICAL
请严格遵守项目上下文强制协议：[specs/PROJECT-CONTEXT.md](specs/PROJECT-CONTEXT.md)
**在执行本 Skill 之前，必须先建立项目认知。**

## 你的任务
根据用户指定的功能和阶段，自动执行对应的开发任务，并在完成后更新任务状态。

## 边界守卫 (Guardrails) - CRITICAL
请严格遵守通用边界守卫规则：[specs/GUARDRAILS.md](specs/GUARDRAILS.md)
**当前阶段**: 编码实现阶段 (Implementation)

## 输入格式
用户会以以下格式提供指令：
- "完成 [功能名] 的任务 第 [N] 阶段"
- "实现 [功能名] 阶段 [N]"
- "开发 [功能名] 的 [阶段名称]"

示例：
- "完成用户登录功能的任务 第1阶段"
- "实现评论功能 阶段2"
- "开发支付功能的数据层"

## 工作流程

### 1. 解析用户指令
从用户输入中提取：
- **功能名称**：例如"用户登录"、"评论功能"
- **阶段标识**：可以是数字（1、2、3）或名称（"数据层"、"表现层"）

### 2. 定位任务规划文档
- 查找 `specs/features/[功能名]_任务规划.md`
- 如果文档不存在，提示用户先执行 `feature-task-planning` Skill

### 3. 读取相关文档
**必须按顺序读取以下文档，建立完整的功能上下文：**

#### 3.1 读取需求文档
- 文件路径：`specs/features/[功能名].md`
- 重点关注：
  - 功能的背景和价值
  - 用户角色和用户故事
  - 核心流程和交互规则
  - 边界情况和异常处理
  - **验收标准（AC）** - 这是实现的目标

#### 3.2 读取技术方案文档
- 文件路径：`specs/features/[功能名]_技术方案.md`
- 重点关注：
  - API 接口定义（路径、参数、响应格式）
  - 数据库设计（表结构、字段、索引）
  - 核心逻辑和算法
  - 异常处理方案
  - 技术难点和解决方案

#### 3.3 读取任务规划文档
- 文件路径：`specs/features/[功能名]_任务规划.md`
- 重点关注：
  - 识别指定阶段的所有任务
  - 提取每个任务的：
    - 任务编号（如 Task-01）
    - 任务标题和说明
    - 涉及文件
    - 参考文档章节
    - 对应的验收标准
    - 依赖关系
    - 验证标准

**如果任何文档缺失，必须停止并提示用户先完成前置步骤。**

### 4. 前置检查
在开始编码前，必须检查：
- [ ] **文档完整性**：需求文档、技术方案、任务规划都已存在
- [ ] **依赖任务**：检查任务规划中的依赖任务是否已勾选完成
- [ ] **项目环境**：项目能否正常启动，依赖库是否安装
- [ ] **上下文理解**：确认已理解需求和技术方案的关键内容

**如果前置条件不满足，必须停止并告知用户。**

### 5. 执行开发任务
按照任务顺序，逐个完成：

#### 5.1 任务开始前
- 向用户确认："即将开始执行 [任务编号]: [任务标题]，是否继续？"
- 说明任务的目标和涉及的文件

#### 5.2 任务执行
- **严格遵守需求文档**：确保实现符合用户故事和验收标准
- **严格遵守技术方案**：按照设计的 API、数据库结构、核心逻辑实现
- **严格遵守项目规范**：遵守技术栈和开发规范
- **优先复用代码**：复用项目中已有的代码、组件、工具函数
- **参考文档章节**：任务中标注的"参考"章节是实现的依据
- **添加注释文档**：编写必要的注释和文档

#### 5.3 任务完成后
**必须按以下顺序执行：**

1. **编写测试文件**
   - 根据任务的验证标准，编写对应的测试
   - 测试类型根据任务性质选择：
     - 数据层任务 → 单元测试（测试 CRUD 操作）
     - API 任务 → 集成测试（测试接口响应）
     - 组件任务 → 组件测试（测试渲染和交互）
     - 工具函数 → 单元测试（测试输入输出）
   - 测试文件命名规范：
     - `tests/unit/[模块名].test.js`
     - `tests/integration/[功能名].test.js`
     - `tests/components/[组件名].test.js`
   - 测试必须覆盖：
     - 正常情况（Happy Path）
     - 边界情况（Edge Cases）
     - 异常情况（Error Cases）

2. **运行测试**
   - 执行刚编写的测试
   - 确保测试通过
   - 如果测试失败，修复代码直到通过

3. **代码自检**
   - 检查代码是否符合项目规范
   - 检查是否有重复代码可以提取
   - 检查注释是否清晰

4. **展示结果**
   - 向用户展示完成的代码
   - 展示测试代码和测试结果
   - 询问用户是否满意，是否需要调整

**重要：如果没有编写测试，任务不算完成。**

### 6. 阶段性验证
当该阶段的所有任务完成后：

1. **运行完整测试套件**
   - 运行该阶段所有任务的测试
   - 确保所有测试通过
   - 检查测试覆盖率（建议 > 80%）

2. **集成测试**
   - 如果该阶段涉及多个模块，进行集成测试
   - 验证模块间的协作是否正常

3. **验收标准检查**
   - 对照需求文档的验收标准
   - 检查该阶段完成的任务是否满足对应的 AC
   - 标记已满足的验收标准

4. **代码质量检查**
   - 运行 Linter（ESLint/Prettier）
   - 运行类型检查（TypeScript）
   - 检查是否有代码异味

5. **生成阶段完成报告**
   - 包含测试结果和覆盖率
   - 包含验收标准检查结果

### 7. 更新任务状态
- 在任务规划文档中，将已完成的任务标记为 `[x]`
- 更新验收标准检查清单的状态
- 保存更新后的文档

### 8. 生成完成报告
- 读取 `assets/stage-completion-report-template.md` 作为模板
- 填充实际的完成信息：
  - 功能名称和阶段信息
  - 已完成的任务列表（包含测试文件和测试结果）
  - 文件变更清单
  - 测试结果和覆盖率
  - 验收标准检查结果
  - 遇到的问题和解决方案
  - 下一步建议
- 保存报告到 `docs/开发记录/[功能名]_阶段[N]_完成报告.md`
- 在对话中向用户展示报告摘要

## 关键规则

### 规则 1：严格遵守任务规划
- 不要跳过任务
- 不要改变任务顺序（除非依赖关系允许）
- 不要做任务规划之外的事情

### 规则 2：代码复用优先
在编写新代码前，必须：
1. 检查项目中是否有类似的实现
2. 检查是否有可复用的组件、工具函数
3. 遵循项目现有的代码模式和风格

### 规则 3：测试驱动质量
每个任务完成后，必须：
- **立即编写测试**：不要等到最后才写测试
- **测试先行验证**：通过测试验证代码正确性
- **覆盖关键场景**：正常、边界、异常情况都要测试
- **测试即文档**：测试代码要清晰易懂

**测试编写原则**：
- 测试文件与源文件对应（如 `user.js` → `user.test.js`）
- 测试描述要清晰（describe/it 语句要说明测试内容）
- 每个测试只验证一个点
- 使用有意义的断言消息

### 规则 4：文档同步
如果代码修改影响了文档，必须：
- 更新相关的 API 文档
- 更新 README（如果需要）
- 在完成报告中说明文档变更

### 规则 5：透明沟通
- 在开始每个任务前，告知用户
- 遇到问题时，及时向用户说明
- 完成后，展示结果并征求反馈

## 异常处理

### 情况 1：文档缺失
```
❌ 错误：缺少必要的文档

检查结果：
- 需求文档 (specs/features/[功能名].md): [✅ 存在 / ❌ 缺失]
- 技术方案 (specs/features/[功能名]_技术方案.md): [✅ 存在 / ❌ 缺失]
- 任务规划 (specs/features/[功能名]_任务规划.md): [✅ 存在 / ❌ 缺失]

请先执行以下步骤：
1. 使用 feature-requirements-clarification 生成需求文档
2. 使用 feature-tech-design 生成技术方案
3. 使用 feature-task-planning 生成任务规划

然后再使用本 Skill 进行编码实现。
```

### 情况 2：依赖任务未完成
```
⚠️ 警告：依赖任务未完成

当前任务 Task-05 依赖于：
- Task-02 (未完成)
- Task-04 (未完成)

建议：
1. 先完成依赖任务
2. 或者调整任务顺序（需要用户确认）
```

### 情况 3：技术方案不明确
```
⚠️ 警告：技术方案细节不足

任务 Task-03 要求实现 XXX，但技术方案中缺少以下信息：
- API 接口定义
- 数据结构设计

建议：
1. 补充技术方案文档
2. 或者根据现有信息做合理推断（需要用户确认）
```

### 情况 4：代码冲突或错误
```
❌ 错误：代码执行失败

错误信息：[具体错误]

可能原因：
1. [原因分析]
2. [原因分析]

建议修复方案：
1. [方案1]
2. [方案2]

是否继续尝试修复？
```

## 输出
- 完成指定阶段的所有代码
- 对应的测试文件
- 更新后的任务规划文档（任务状态已勾选）
- 阶段完成报告（保存到 `docs/开发记录/[功能名]_阶段[N]_完成报告.md`）

## 注意事项
1. **不要一次性完成所有阶段**：每次只执行用户指定的阶段，避免一次性生成过多代码
2. **保持增量式开发**：每个任务完成后都要验证，而不是等到最后
3. **尊重用户反馈**：如果用户对某个任务的实现不满意，立即调整
4. **记录变更**：所有代码变更都要在完成报告中说明

## 最终交付
- 完成指定阶段的所有代码
- 更新后的任务规划文档（任务状态已勾选）
- 阶段完成报告
- 相关测试结果（如果有）
