# AI 工作流介绍

## 制作工作流的原因
我使用过市面上大多数的 AI 工作流，但体验往往达不到自己想要的效果，所以自己研发了一套工作流。整体思路基于 Kiro Spec 模式，通过结构化的方式引导 AI 完成从需求到实现的全过程。

## 核心设计理念

### 1. 文档驱动开发
所有决策和实现都基于文档，确保可追溯性和一致性。

### 2. 阶段分离
每个 Skill 职责单一，避免"过度热心"导致的流程混乱。

### 3. 强制上下文建立
通过 `specs/PROJECT-CONTEXT.md` 协议，强制 AI 在新窗口中先了解项目背景再开始工作。

### 4. 引导式交互
使用苏格拉底式提问和示例驱动，降低用户决策难度。

## 工作流结构

这套工作流分为三个层级：

### 一、项目级别工作流（项目启动时使用）

项目级别的 Skill 一般只在项目开始时使用一次，用于建立项目的基础框架和规范。

执行顺序：需求澄清 → 产品概述 → 技术栈选型 → 目录结构 → 开发规范 → 路线图规划 → 项目初始化

#### 1. project-requirements-clarification（需求澄清）
**用途**：挖掘用户的项目想法

作为新手用户，可能只有一个简单的想法，比如"我想开发一款微信"。这个 Skill 会像一个好奇的合伙人一样，通过苏格拉底式提问，从 WHY/WHO/WHAT/HOW 四个维度引导用户思考，最终生成一份详细的需求澄清文档。

**输出**：标准化的项目描述文本

#### 2. project-product-overview（产品概述）
**用途**：将需求转化为标准化的产品文档

把需求澄清文档转化为产品概述文档，明确项目的愿景、核心价值、目标用户、核心板块和验收标准。这份文档将作为后续所有决策的基石。

**输出**：`specs/产品概述.md`

#### 3. project-tech-stack（技术栈选型）
**用途**：推荐最合适的技术栈

基于产品概述，自动推荐最成熟、最稳定的技术方案（而非最热门的）。会详细说明为什么选择这套技术栈，帮助 AI 在后续开发中遵守技术约束。

**输出**：`specs/技术栈.md`

#### 4. project-structure（目录结构）
**用途**：设计项目的目录结构

根据产品概述和技术栈，生成高内聚低耦合的目录结构。这个文档帮助 AI 快速了解项目的组织方式和模块划分。

**输出**：`specs/项目结构.md`

#### 5. project-dev-standards（开发规范）
**用途**：制定代码规范和协作流程

基于技术栈，制定具体的代码风格、命名约定、Git 提交规范和 AI 交互协议。确保代码风格统一且可维护。

**输出**：`specs/开发规范.md`

#### 6. project-roadmap-planning（路线图规划）
**用途**：规划开发顺序和里程碑

分析模块间的依赖关系，制定合理的开发路线图，解决"先做什么，后做什么"的问题。将功能划分为 MVP、完整版、增强版等里程碑。

**输出**：`specs/开发路线图.md`

#### 7. project-initialization（项目初始化）
**用途**：执行实际的项目脚手架创建

严格按照前面生成的文档，执行项目初始化操作：创建目录结构、配置文件、初始化 Git 仓库等。这是唯一一个"执行"类的 Skill。

**输出**：项目骨架代码 + `docs/开发记录/初始化记录.md`

---

### 二、功能级别工作流（开发具体功能时使用）

功能级别的 Skill 用于开发具体的功能模块，可以反复使用。

执行顺序：功能需求澄清 → 技术方案设计 → 任务规划 → 编码实现
迭代顺序：功能迭代变更 → 编码实现（对已完成功能进行增量修改时）

#### 1. feature-requirements-clarification（功能需求澄清）
**用途**：将模糊的功能想法转化为清晰的需求文档

当用户说"我想做一个评论功能"时，这个 Skill 会通过引导式提问，明确场景、用户、流程、边界和验收标准。

**输出**：`specs/features/[功能名].md`

#### 2. feature-tech-design（技术方案设计）
**用途**：设计功能的技术实现方案

基于需求文档，设计 API 接口、数据库表结构、核心逻辑和异常处理。确保每个验收标准都有对应的技术实现。

**输出**：`specs/features/[功能名]_技术方案.md`

#### 3. feature-task-planning（任务规划）
**用途**：拆解为可执行的开发任务

将技术方案拆解为细粒度的任务清单（每个任务 < 2 小时），标注依赖关系、风险点和验证标准。

**输出**：`specs/features/[功能名]_任务规划.md`

#### 4. feature-evolution（功能迭代变更）
**用途**：对已完成开发闭环的功能进行增量修改

当你完成了某个功能的全流程（需求 → 技术方案 → 任务规划 → 编码），之后又产生了新的想法或修改需求时，使用这个 Skill。它会自动读取已有的功能文档，分析变更影响范围，增量更新文档，并只生成变更相关的新任务——而不是推倒重来。

**变更分类**：
- **微调 (Tweak)**：不涉及新 AC，仅调整现有行为 → 就地修改受影响文档 + 追加小任务
- **扩展 (Extension)**：新增 AC 或 API → 增量更新需求 + 技术方案 + 任务
- **重构 (Refactor)**：改变数据结构或核心逻辑 → 全文档增量更新 + 兼容性方案

**输出**：`specs/features/[功能名]_变更任务_{CR序号}.md`

#### 5. feature-implementation（编码实现）
**用途**：执行具体的开发任务

这是一个智能执行器，用户只需说"完成 XX 功能的任务 第几阶段"，Skill 会自动：
- 读取对应的任务规划文档
- 识别该阶段的所有任务
- 按顺序执行开发任务
- 完成后自动更新任务状态
- 生成阶段完成报告

**使用示例**：
- "完成用户登录功能的任务 第1阶段"
- "实现评论功能 阶段2"
- "开发支付功能的数据层"

**输出**：
- 完成的代码
- 更新后的任务规划文档（任务已勾选）
- 阶段完成报告

---

### 三、通用工作流（随时使用）

#### bugfix-workflow（BUG 修复）
**用途**：标准化的 BUG 修复流程

强制执行：复现 → 定位 → 修复 → 单元测试 → 验证 → 生成报告。确保每个 BUG 都有完整的修复记录和测试覆盖。

**输出**：`docs/BUG修复文档/[日期]-[问题简述].md`

## 核心机制

### 1. 边界守卫（GUARDRAILS）
通过 `specs/GUARDRAILS.md`，严禁 AI 越过当前 Skill 的职责范围。防止"过度热心"导致在错误阶段做错误的事。

### 2. 项目上下文协议（PROJECT-CONTEXT）
通过 `specs/PROJECT-CONTEXT.md`，强制 AI 在新窗口中先建立项目认知。使用情感绑架、同行压力、奖励机制等多种技巧，确保 AI 遵守。

### 3. 通用 Agent 规则
通过 `通用Agent.md`，定义所有 AI 必须遵守的基本规则：
- 始终使用中文
- 确认优先，禁止直接开干
- 文档与代码必须同步
- 强制使用最新文档

## 使用场景

### 场景 1：从零开始一个新项目
1. 使用项目级别工作流（1-7）完成项目初始化
2. 使用功能级别工作流开发第一个功能
3. 后续功能重复使用功能级别工作流

### 场景 2：为现有项目添加新功能
1. 跳过项目级别工作流（如果文档已存在）
2. 直接使用功能级别工作流

### 场景 3：对已完成的功能进行修改或扩展
1. 使用 feature-evolution 进行变更影响分析和增量任务规划
2. 使用 feature-implementation 执行增量任务

### 场景 4：修复 BUG
直接使用 bugfix-workflow

---

## 工作流的优势

1. **新手友好**：通过引导式提问，降低决策难度
2. **结构化思考**：强制在正确阶段做正确的事
3. **文档驱动**：确保可追溯性和一致性
4. **上下文感知**：避免 AI 在新窗口中"失忆"
5. **质量保证**：每个阶段都有明确的输出和验证标准

---

## 快速开始

1. 克隆或下载这个工作流
2. 在 Kiro 中打开对应的 Skill 文件
3. 按照 Skill 中的指引与 AI 交互
4. AI 会自动生成文档到 `specs/` 目录

**记住**：每个 Skill 都会强制 AI 先读取项目上下文，所以即使在新窗口中，AI 也能理解你的项目。
